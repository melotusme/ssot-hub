# SSOT Hub 重构设计（草案，2026-11-05）

基于 0.2.2（commit 7fb077d）的代码 review。目的是先把"要解决什么问题"和"数据怎么组织"想清楚，再动代码。标注【待定】的地方需要你拍板。

---

## 1. 现状一句话

一个通用的「资产 + 字符串字段 + 自由关系」台账，19 种类型；桌面端 Rust + SQLite、Web 端 TS + IndexedDB 各实现了一遍完整的业务规则；整库作为一个 JSON 快照读写、备份、同步。快捷键编辑是挂在同一个应用里的另一个独立工具。

## 2. 主要问题

### 2.1 产品层：范围在长，核心没收敛

- 最早的问题是「换机 / 续费 / 账号恢复时，知道自己有什么、依赖什么」。0.2 又加进了家庭成员、班课、游戏资源副本、网络穿透、个人 Agent，19 种类型平铺在侧栏，没有主次。
- 每种类型都是「填表」，但没有围绕具体场景的视图。比如"这台电脑要换掉，影响什么"、"下个月要续哪些费、一共多少钱"、"孩子还剩多少课时"，都要自己翻列表拼。
- 机器扫描的数据和人工台账混在一起：现有私有盘点里 Mac 有 529 条软件，PVE 有 1579 条。这些一旦导入，软件列表会淹没其他所有记录，而其中绝大多数没人会去补用途或配置。

### 2.2 数据模型：关系被当成资产存

- 关系有两套机制：
  1. 字段引用（`device_id`、`owner_id` 等，语义固定，可校验）；
  2. 自由 `links`（`relation` 是任意文本，例如 demo 里把数据塞进关系名：`使用路径：~/.config/editor`）。
- `assignment`（使用记录）、`copy`（资源副本）、`connection`（节点接入）本质上是「两个实体之间、带属性和时间区间的关系」，现在却作为第 15、17、19 种"资产"出现在侧栏里，和设备、账号并列。
- 所有字段都是 `Record<string, string>`：价格、课时、日期、枚举全是字符串，规则靠散落在校验函数里的 `if (key === "price")` 维持。

### 2.3 前后端交互：同一套规则写了两遍，已经不一致

| 规则 | Web（`validation.ts` / `web-store.ts`） | 桌面（`store.rs`） |
| --- | --- | --- |
| 字段白名单 | 从 `model.ts` 的 `fields` 推出 | `allowed()` 手写一份 |
| 引用类型 | `field.ref` | `ref_kind()` 再手写一份 |
| 名称长度上限 | 200 字符 | 500 字节 |
| 删除 | 不检查阻塞，删完靠全量校验报"引用无效" | 先算阻塞，有引用直接拒绝 |
| 日期字段 | 按 `type: "date"` | 硬编码字段名列表 |

加一个字段要同时改 `model.ts`、`store.rs` 的 `allowed()`、必要时 `ref_kind()`，漏改一处只会在另一端运行时才暴露。

其他交互问题：

- **命令是"字符串名 + 无类型参数"**。`webCommand` 是一个约 200 行的 if-else；Rust 和 TS 之间没有共享类型（没有 specta / ts-rs），参数名拼错只能运行时发现。
- **SQLite 只用了一行**：`state(id=1, body TEXT)` 存整份 JSON。每次改一个字段都要：读出整库 → 反序列化 → 全量校验 → 序列化 → 整行写回 → 把整份快照返回给前端。
- **全量校验是 O(n²)**：每个引用字段都在所有资产里线性查找，使用记录还有两两比较。几十条没问题，导入 2000 条软件后每次编辑都会明显变慢。
- **审计日志无限增长且在快照里**：`events` 和资产存在同一个 JSON 里，一起备份、一起同步。桌面导入时 detail 写入「全部资产的 before + after」，一次导入 2000 条软件，日志就多出约 4000 条资产的副本。
- **两条相近的替换路径**：`restore_snapshot`（只允许空库）和 `replace_snapshot`（先备份再覆盖）语义重叠，界面上也分在两个面板。
- **前端**：`App.tsx` 2067 行，一个组件里 20 多个 `useState`，列表、编辑、导入、删除、恢复都在里面。

### 2.4 同步

整库加密快照 + WebDAV 手动上传 / 下载、一次只在一端编辑。对个人使用方向是对的，加密和冲突检测做得很谨慎。问题在于：

- "一次只在一端编辑"只写在文档里，没有机制提醒（另一台机器正在编辑时没有任何提示）；
- 审计日志随快照同步，体积会越来越大；
- 没有记录级的 `updatedAt / 修改设备`，以后想做合并没有基础。

### 2.5 快捷键模块

它的 SSOT 是 Lua / AHK 源码，和台账不共享任何数据，质量本身不错（不执行脚本、span 级局部改写、SHA256 版本校验）。但它让"资产台账"这个产品多了一个不相关的入口，也是 `shortcuts.rs`（929 行）+ `ShortcutsPage.tsx`（775 行）的维护面。

## 3. 先回答的产品问题【待定】

建议用 3 个核心场景收敛范围，其他类型降为"次要"或推后：

1. **换机 / 重装 / 退役**：这台设备上有哪些系统、装了哪些*我关心的*软件、配置从哪恢复、哪些账号登录在上面。
2. **续费与花费**：未来 30 / 90 天要续什么，按月折算一共多少钱，谁的账号在付。
3. **家庭归属**：每台设备 / 硬盘现在归谁、谁在用、历史怎么交接过。

对应的取舍建议：

| 类型 | 建议 |
| --- | --- |
| 设备、系统环境、存储、账号、订阅、成员 | 核心，保留 |
| 配置来源、手机号、eSIM、域名、服务器 | 保留，作为核心实体的附属 |
| 软件安装 | 拆成两层：扫描清单（只读、不进主列表）+ 关注的软件（人工提升后才进台账） |
| 使用记录、资源副本、节点接入 | 改为「关系」，不再是侧栏里的资产类型 |
| 班课 | 【待定】和数字资产关系很弱，建议推后或做成独立小模块 |
| 资源目录、网络、个人 Agent | 【待定】先合并成"其他服务 / 资源"一个通用类型，等真有查询需求再细分 |

## 4. 目标架构

### 4.1 数据模型：实体 / 关系 / 观测 三层

```
Entity      实体：设备、环境、存储、账号、订阅、成员……
            { id, kind, name, status, attrs(按类型有结构), updatedAt, updatedBy }

Relation    关系：两实体间有类型、可带属性和时间区间的事实
            { id, type, from, to, attrs, validFrom?, validTo?, updatedAt, updatedBy }
            type 是封闭枚举：uses(使用)、owns(产权)、runs_on(运行于)、
            installed_in(安装于)、logged_in(登录于)、recovers(恢复手段)、
            pays_for(付费)、stores(副本存放)、joins(接入网络)、config_path(使用路径)……
            每个 type 规定允许的 from/to 类型和属性。

Observation 观测：扫描器 / 导入器的原始结果，单独存放
            { source, observedAt, key, payload }
            和台账对账："新出现 / 已消失 / 有变化"，用户确认后才提升或更新实体。
```

这样：

- 使用记录 = `uses` 关系（成员 → 设备，属性：主力 / 备用 / 共用，区间 `[validFrom, validTo)`）。交接 = 结束一条、开始一条，规则写在关系类型上。
- 现在的 `device_id`、`owner_id` 这类字段引用也统一迁成关系，"双向查询"和"删除阻塞"只需要查一张关系表。
- 自由文本关系取消；确实需要备注时放在关系的 `note` 属性里。
- 2000 条软件扫描结果待在观测层，不污染台账，也不进同步快照（或可选进）。

### 4.2 单一 schema，单一业务实现

定义一份 schema（TS 对象或 JSON），描述：实体类型、字段（类型：text / date / money / int / enum）、关系类型及端点约束、业务规则（区间不重叠、课时不超额等）。表单、列表列、筛选维度、校验全部从它派生。

**已定（2026-11-05）：只在桌面编辑，业务逻辑只在 Rust 写一份。**

- schema 定义在 Rust（例如 `schema.rs` 里的常量表），是字段、关系类型和业务规则的唯一来源。前端启动时通过一个 `schema()` 命令取回，用来渲染表单、列表列和筛选项，不再在 `model.ts` 里另写一份字段表。
- 所有写操作、校验、删除阻塞计算、使用区间检查、费用计算只在 Rust。前端可以做"必填为空"这类即时提示，但不做权威校验。
- 删除的 Web 端代码：
  - `src/web-store.ts`、`src/validation.ts` 及其测试（`web-store.test.ts`、`WebApp.test.tsx`、`family.test.ts` 中针对 Web 存储的部分，改写为 Rust 测试）；
  - `api.ts` 里的浏览器分支（`webCommand`、浏览器文件选择和下载）；
  - `sync.ts` 里的浏览器 WebDAV 传输（`browserTransport`）和对 `validateSnapshot` 的调用（解密后的快照交给 Rust 的 `replace_snapshot` 校验）；
  - PWA 相关文件（`pwa.ts`、`public/sw.js`、`manifest.webmanifest`），以及 README 和同步契约里关于浏览器、CORS、手机 PWA 的说明。
- 界面里约 28 处 `desktop ? … : …` 分支一并去掉。
- **手机查看**（可选，排在最后）：桌面端提供"导出只读页面"，生成一个自包含的 HTML（数据已解密内嵌，或打开时输入口令解密），手机上用浏览器或文件 App 打开即可浏览，不能修改。它只读快照，不需要任何校验逻辑。

**加密的位置**：加解密目前在前端用 WebCrypto 做。只有桌面后可以移到 Rust（`aes-gcm` + `pbkdf2`），口令只经过一次 IPC 传给后端，前端不再接触明文快照以外的密文处理；格式 `ssot-encrypted-v1` 保持不变，已有云端文件照常可读。这一步不是必须的，可以放到同步那一步再做。

### 4.3 存储

- SQLite 拆真实表：`entities`、`relations`、`events`、`observations`，按记录读写；revision 改成每条记录的 `version` 或保留全局 revision 都可以。
- 不再需要 IndexedDB；已在浏览器里录入的数据，先用旧版 Web 端"导出"成快照，再在桌面端恢复。
- 审计日志单独存，只记改动的字段 diff，不再整库 before / after；可设保留期限，默认不进同步快照。
- 校验改为按需：只校验被修改的记录及其关系，用 id 索引代替线性查找。

### 4.4 前后端接口

- 一个类型化的客户端：`api.entities.save(e)`、`api.relations.end(id, date)`……替代字符串命令。
- 用 `tauri-specta` 从 Rust 命令和结构体生成 TS 类型和调用函数，杜绝参数名错位；`api.ts` 只剩一层薄封装。
- 写操作返回变更的记录而不是整份快照；前端按 id 更新局部状态。

### 4.5 同步

保留现有加密快照 + WebDAV 的单写者模式，补三点：

1. **编辑租约**：在 WebDAV 目录写一个 `lease.json`（设备名、时间）。另一台机器打开时提示"MacBook-A 在 2 小时前开始编辑，确认接手？"——把"一次只在一端编辑"从文档变成机制。
2. 每条记录带 `updatedAt / updatedBy`，为以后做记录级合并（同一条记录冲突才需要人工处理）留基础。
3. 快照默认不带审计日志和观测数据。

### 4.6 前端结构

按功能拆目录：`entities/`（列表、详情、编辑）、`relations/`（关系编辑、交接）、`inventory/`（扫描对账）、`renewals/`（续费视图）、`data/`（备份、恢复、同步）、`shortcuts/`。`App.tsx` 只留布局和路由。列表继续用现有 `RecordList`。

围绕第 3 节的场景加专门视图：设备详情页（系统、软件、账号、配置、使用历史一页看完）、续费日历 / 月度费用、成员视图（每个人名下和在用的东西）。

### 4.7 快捷键【待定】

建议拆成独立的小应用或独立仓库：它不依赖台账，拆开后两边都更简单。若想保留在同一个应用，至少放在单独的路由和目录，不和台账共用状态。

## 5. 迁移步骤

每一步都可以单独发布，旧快照通过迁移脚本升级，不丢数据。

1. **定范围**：确认第 3 节的取舍（4.2 已定为只在桌面编辑）。
2. **去掉 Web 端 + schema 收到 Rust**：先不改存储。把 Web 端 `ssot-hub-v2` 里已有的数据导出备份；删除 4.2 列出的 Web 代码；把字段表移到 Rust 并通过 `schema()` 命令给前端；接入 `tauri-specta`。完成后两端不一致的问题自然消失。
   **已完成（2026-11-05，未提交）**：
   - `src-tauri/src/schema.rs` 是字段的唯一来源；`store.rs` 的白名单、引用类型、选项校验都从它推导，删掉了手写的 `allowed()` / `ref_kind()`。校验改用 id 索引，不再逐条线性查找。
   - 新增 `schema`、`check_snapshot` 命令。解密后的同步快照先交给 Rust 校验再预览。
   - `tauri-specta`（`=2.0.0-rc.26`）生成 `src/bindings.ts`；前端改为 `commands.save_asset(asset, revision)` 这样的带类型调用，类型检查当场发现并修正了快捷键 `engine` 字段两端定义不一致。
   - 两个"是否最新"的 cargo 测试：`schema_fixture_is_current`（前端测试用的 schema 快照）和 `bindings_are_current`。改了 Rust 命令或字段后运行 `UPDATE_BINDINGS=1 UPDATE_SCHEMA=1 cargo test`。
   - 删除 Web 存储、Web 校验、PWA、浏览器 WebDAV 传输（移到 `scripts/fetch-transport.ts` 供验证脚本使用），CI 不再打包 Web。
   - 规则变化：所有下拉字段都校验取值（以前 Rust 只校验其中几个）；名称上限统一为 500 个字符；新增可见的"备注"字段。
3. **关系模型**：新增类型化关系；把 `assignment / copy / connection` 和字段引用迁成关系；自由 links 迁到对应类型或 `note`。快照升到 v4，带 v3 → v4 迁移和测试。
4. **观测层**：扫描结果写入观测表，做"对账"界面；软件只有在提升后才进台账。
5. **存储拆表 + 审计瘦身**：SQLite / IndexedDB 按记录存储，审计只记 diff。
6. **前端拆分 + 场景视图**。
7. **同步租约 + 记录元数据**（可顺带把加解密移到 Rust）。
8. **可选：导出只读页面**给手机查看。
9. 快捷键是否拆出，按 4.7 的决定执行。

## 6. 本次 review 顺带发现的小问题

- Web 端 `delete_asset` 没有先检查引用阻塞，错误提示是"xxx 引用无效"，看不出是哪条记录在引用。
- 名称长度上限两端不同：TS 是 200 个字符，Rust 是 500 **字节**（中文约 166 字）。英文长名称桌面能存、同步到 Web 时整份快照校验失败无法应用；中文 170–200 字的名称则反过来，Web 能存、桌面拒收。
- `scripts/collect-estate.mjs` 尚未提交。
- 本地 `node_modules` 不存在，`bun run test` 无法运行（需要先 `bun install`）。
